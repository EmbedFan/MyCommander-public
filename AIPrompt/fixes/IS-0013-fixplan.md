# Fix Plan — IS-0013

Source: `AIPrompt/issue_fix_requests.md`

> Installer does not install the implemented plugins. (exception: ExamplePlugin)

## Summary

Confirmed by reading `Source/MyCommanderSetup/` directly: `MyCommanderSetup` embeds exactly three
files as RCDATA resources — `MyCommander.exe`, `USERGUIDE.md`, `LICENSE` — and nothing else.
**No plugin DLL of any kind is ever bundled or installed**, including `ExamplePlugin`; the
installer has no code path that even looks at a `Plugins` folder. (`ExamplePlugin.vcxproj` is, like
`ZipPlugin.vcxproj`, a standalone project outside `MyCommander.sln` — neither is built or copied by
the installer's own build step today.) The issue's "(exception: ExamplePlugin)" most likely reflects
the reporter's own local `Build\x64\Release\Plugins\` folder happening to already contain
`ExamplePlugin.dll` from a separate manual build at the time they ran the installer, not any special
handling by the installer itself — there is none, for any plugin.

**Fix:** bundle `ZipPlugin.dll` — the one currently real, user-facing ("implemented") plugin — into
the installer's payload and extract it to `<installPath>\Plugins\ZipPlugin.dll`, using the exact
same "always freshly rebuilt, never whatever's already sitting in `Build\\`" discipline
`Tools/RebuildReleaseForInstaller.ps1` already enforces for `MyCommander.exe` itself (INST-006).
`ExamplePlugin` stays excluded, correctly — it's a developer-facing template/reference for writing a
plugin (see its own role in `DEVELOPER_GUIDE.md`), not a feature meant to ship to end users.

## Current behavior

- `Source/MyCommanderSetup/MyCommanderSetup.rc` declares three `RCDATA` resources:
  `IDR_PAYLOAD_MYCOMMANDER`, `IDR_PAYLOAD_USERGUIDE`, `IDR_PAYLOAD_LICENSE`
  (`resource.h` IDs 101-103), sourced from `payload\MyCommander.exe`/`USERGUIDE.md`/`LICENSE`.
- `Tools/RebuildReleaseForInstaller.ps1` (wired as `MyCommanderSetup.vcxproj`'s `PreBuildEvent`,
  INST-006) force-rebuilds only the `MyCommander` target of `MyCommander.sln` via
  `/t:MyCommander:Rebuild`, then copies `Build\x64\Release\MyCommander.exe` plus the repo root's
  `USERGUIDE.md`/`LICENSE` into `Source\MyCommanderSetup\payload\`. It never touches
  `ZipPlugin.vcxproj`, `ExamplePlugin.vcxproj`, or any `Plugins` folder.
- `RunInstall()` (`main.cpp:245-`) calls `ExtractResourceToFile` three times (one per RCDATA
  resource above) into `installPath`, and nothing else ever writes to a `Plugins` subfolder there.
- Confirmed `ComputeInstalledSizeKB` (recursive) and `RunUninstall`'s per-top-level-entry
  `fs::remove_all` loop both already handle an arbitrary subfolder like `Plugins\` correctly with
  **no change needed** — they're generic over whatever ends up under `installPath`.

## Design

1. **`Tools/RebuildReleaseForInstaller.ps1`**: after the existing `MyCommander` rebuild, also
   force-rebuild `Source\ZipPlugin\ZipPlugin.vcxproj` as `Release|x64` (same
   fresh-rebuild-not-whatever's-already-there discipline), then copy its output
   (`Source\ZipPlugin\Build\x64\Release\ZipPlugin.dll`) into `payload\ZipPlugin.dll`. A failed
   plugin rebuild should **not** abort packaging the installer the way a failed `MyCommander`
   rebuild already does (`exit 1`) — the app is fully usable with zero plugins installed (this is
   already true today, since nothing installs any), so a broken plugin build should downgrade to a
   loud warning, not block shipping the installer for the core app.
2. **`Source/MyCommanderSetup/resource.h`**: add `#define IDR_PAYLOAD_ZIPPLUGIN 104`.
3. **`Source/MyCommanderSetup/MyCommanderSetup.rc`**: add
   `IDR_PAYLOAD_ZIPPLUGIN RCDATA "payload\\ZipPlugin.dll"`.
4. **`Source/MyCommanderSetup/main.cpp`**'s `RunInstall()`: after the existing three
   `ExtractResourceToFile` calls (which still hard-fail the install on failure, unchanged — they're
   the core app itself), add one more extracting into the `Plugins` subfolder:
   ```cpp
   if (!ExtractResourceToFile(IDR_PAYLOAD_ZIPPLUGIN, fs::path(installPath) / L"Plugins" / L"ZipPlugin.dll")) {
       SayError(L"Warning: could not install the ZIP plugin -- MyCommander will still work without it.\n");
   }
   ```
   `ExtractResourceToFile` already calls `fs::create_directories(destPath.parent_path(), ec)`
   internally, so the new `Plugins` subfolder is created automatically — no separate
   `create_directories` call needed. Deliberately a **warning, not a hard failure**: a missing or
   corrupt plugin payload shouldn't block installing the core app, consistent with how the app
   itself already treats an empty/missing `Plugins` folder at runtime as the normal, unremarkable
   case (`PluginManager::DiscoverAndLoad`'s own "safe to call with a nonexistent pluginsDir" note).
5. **Payload staleness check**: `payload/README.txt` already documents why the committed `payload\`
   files are placeholders, regenerated by the `PreBuildEvent` before every real build — add one
   line noting `ZipPlugin.dll` now follows the same convention.

### Scope decision: hardcoded to `ZipPlugin`, not a generic "embed every plugin" pipeline

There is exactly one real, user-facing plugin today. A fully generic mechanism (scanning
`Build\x64\Release\Plugins\*.dll` and dynamically generating the `.rc`/extraction list to match
however many plugins happen to exist at build time) would need either a build-time-generated `.rc`
include or a packed multi-file resource format — meaningfully more machinery than today's actual
need, and against this project's own stated preference for not designing ahead of a real
requirement. The chosen fix follows the **exact same shape already established** for
`USERGUIDE.md`/`LICENSE` (one named resource, one named extraction call) — adding a second real
plugin later is a small, obvious, three-line-per-file extension of this same pattern, not a
redesign.

## Test plan

No existing `SetupLogicTests.cpp` coverage applies here — matching this project's own established
precedent (`main.cpp`'s *other* three `ExtractResourceToFile` calls, the registry writes, and the
shortcut creation are all real-OS-side-effect code with no headless test coverage either, per
`Elevation.h`'s own `RunElevated` precedent that CLAUDE.md's Testing section already documents).
Manual verification: run `Tools/RebuildReleaseForInstaller.ps1` (or build `MyCommanderSetup`, which
triggers it), confirm `payload\ZipPlugin.dll` appears; run the built `MyCommanderSetup.exe`, confirm
`<installPath>\Plugins\ZipPlugin.dll` exists after install and that the installed `MyCommander.exe`
actually loads it (its own startup log, if `logLevel` is enabled, or simply that "Pack file"/"Unpack
Package"/"Archive info" appear on the File menu); uninstall and confirm the `Plugins` folder is
removed along with everything else.

## Risk / scope notes

- Entirely additive to the installer — no change to how the main `MyCommander.exe` payload is
  built, validated, or extracted, and no change to uninstall logic (already generic enough to need
  none, confirmed above).
- The non-fatal warning-on-plugin-failure design means a broken/missing `ZipPlugin.vcxproj` build
  can never block shipping or running the installer for the core app — the worst case is "installed
  without the ZIP plugin," which is also exactly today's status quo for every user.
- Touches `Tools/RebuildReleaseForInstaller.ps1`, which already has `$ErrorActionPreference = 'Stop'`
  — the new plugin-rebuild step must be wrapped so its own failure doesn't propagate as a script-
  terminating error the way the existing `MyCommander` rebuild's failure deliberately does (that one
  should still hard-stop; the new one should not).

## Status

**Implemented** (2026-10-02), per the design above, with no deviations:

- `Tools/RebuildReleaseForInstaller.ps1` now rebuilds `ZipPlugin.vcxproj` Release|x64 and stages
  `ZipPlugin.dll` into `payload\`, wrapped in `try`/`catch` so a failure degrades to a
  `Write-Warning` rather than aborting the script (the existing `MyCommander` rebuild's own
  `$ErrorActionPreference = 'Stop'`/explicit `exit 1` on failure is unchanged).
- `resource.h`/`MyCommanderSetup.rc` gained `IDR_PAYLOAD_ZIPPLUGIN` (104); `main.cpp`'s
  `RunInstall()` extracts it into `<installPath>\Plugins\ZipPlugin.dll`, warning (not failing) if
  that one extraction fails.
- New `INST-007` requirement added to `AIPrompt/my-commander.md` (`Implemented`); `README.md`'s
  Installing section and `payload/README.txt` both updated to mention it.
- **Verified end-to-end, without running the real interactive installer** (which would write to
  `%LOCALAPPDATA%`, the registry, and create a real desktop shortcut — a system-level change, not
  something to do just to verify a build): built `MyCommander.sln` Debug|x64, which triggers
  `MyCommanderSetup`'s `PreBuildEvent` — confirmed in the build log that `ZipPlugin.vcxproj` is now
  rebuilt as Release|x64 and "ZIP plugin staged in ...\payload" is printed; confirmed
  `payload\ZipPlugin.dll` exists on disk; then extracted the compiled-in `IDR_PAYLOAD_ZIPPLUGIN`
  `RCDATA` resource directly from the built `MyCommanderSetup.exe` via `FindResourceW`/
  `LoadResource` (the same Win32 APIs `ExtractResourceToFile` itself uses) into a throwaway temp
  file and confirmed its SHA-256 hash is byte-identical to `payload\ZipPlugin.dll` — i.e. the
  resource compiles in correctly and is extractable, without touching any real install location.
  `MyCommanderTests.exe`: 425 test cases, 11,795 checks, 0 failed (unchanged — no new pure-logic
  module, matching this plan's own "no automated test coverage applies here" note).
- Actually running `MyCommanderSetup.exe` interactively to confirm `<installPath>\Plugins\
  ZipPlugin.dll` appears after a real install, and that the installed app then loads it, remains
  outstanding — left to the user, since performing a real per-user install/registry-write/desktop-
  shortcut creation wasn't done without being asked.
